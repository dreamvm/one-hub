# 月末自动账单选择上月

## 问题与修复

`InsertStatisticsMonth` 原先先对今天执行 `AddDate(0,-1,0)`，再取该结果所在月份的一日。
当上月没有对应日号时，日期归一化可能回到本月；例如2026-03-31会落到三月，进而选择
三月一日，生成尚未结束的本月账单，或把本月已有历史误当成上月已完成。

启用月账单时启动路径会调用该函数；定时任务源码使用每日04:00的 `DailyJob`，
虽然旁边旧注释写“每月一号”，实际并非只会在一号调用。不能用该注释排除月末路径。

修复直接使用 `time.Date(now.Year(), now.Month()-1, 1, ...)` 选择上月一日，仍沿用本地时区、
既有历史检查及汇总函数。入口依旧使用 `time.Now()`；增加私有带时间参数的实现，
测试通过只编入测试二进制的导出包装传入固定日期，不改变生产接口或定时频率。

## 2026-10-01 本地证据

基线为提交错误候选 `34a835004d1c9bc54945d4317ace5d707b6b2188`。
先只抽取原有逻辑并传入固定时钟，保留旧 `AddDate` 计算，再运行真实临时数据库生成：
12个日期中4个正常控制通过、8个月末失败，后者读取到本月模型和900额度，预期为上月模型和100额度。
这一复现使用行为保持的测试入口，不是修改系统时间或声称在当前日期触发旧生产二进制。

候选覆盖年界、平年二月底、闰年二月底和30/31天转换；每个日期实际生成两次，
只留下正确上月账单和一条生成历史。本地 SQLite 12日期均通过，连同提交错误、账单详情及生成
专项共21子例带 race 通过。PostgreSQL18.4 新建临时集群的12日期及6个既有账单子例带 race 通过，
随机回环端口，连接/内存/执行时限受限，运行后正常关闭；MySQL与CI固定PostgreSQL18.0仍待候选CI。
五包离线race、固定Task/Compose策略、相关vet和providers/relay编译退出码均为0。
一次未参与实现的独立只读审阅无具体发现，复用上下文、非fresh-context；独立格式检查通过，
源码、调用方、测试与日志均已审阅，未由审阅者重跑数据库测试。

## 保留范围

不重写已经生成的真实历史账单，不推断其归属和金额；如需核对过去错误月份，先保留证据和备份，
依据实际消费日志及月份政策处理。本项不确定新的跨数据库日统计时区规则，不覆盖所有DST/时区转换，
也不改变并发生成、启动错误观察和提交结果不确定的既有边界。
回滚代码会恢复月末月份选择错误；无数据库结构变化。未发布、部署或调用真实付费服务。
