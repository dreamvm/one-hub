# C1g：Realtime 预留与连接结算

每次渠道选择后，先取得数据库预留再拨号上游。付费会话至少预留一个额度单位，
免费模型和零倍率分组不预留。失败拨号、未携带用量的异常/超时首帧释放预留，
重试重新按所选渠道价格申请；首帧已报告的用量不能被重试抹去。

按 token 计费时，累计收到的 usage 按最终结算同一方式计价，避免逐事件向上取整累计误差。
累计费用达到已预留额度时，申请“已发生费用 + 一个初始预留窗口”的差额；
账户和有限令牌通过同一条件事务裁决，与 Redis 是否启用无关。
续额失败立即关闭上游，再尝试通知客户端。最终仍按实际已报告用量结算，不能截断为预留金额。
按次计费保持每个会话一次费用，不随响应次数重复预留。

WebSocket 两个方向都有读写期限。任一方向退出关闭连接，主处理器等待两个 worker
都结束后同步结算一次；不再让后台结算协程与 usage 更新或 Gin context 回收并发。
初始帧使用 `connect_timeout` 等待期限，缺失 response 的 `response.done` 返回协议错误。

## 验证与兼容

- 本机 WebSocket 验证拒绝时零上游握手、正常多轮用量、令牌耗尽、拨号失败、首帧错误/超时、
  重试、首帧用量和请求结束前完成结算。
- 阻塞 usage callback 验证主处理器等待；16 MiB 模拟慢客户端下载验证预算失败后及时关闭上游。
- SQLite + Redis Hook 验证 Redis / batch 开关、有限/无限、token/小数/按次/免费/零估算费用及续额数据库错误。
- 独立审阅提出零倍率兼容和慢客户端延迟关闭问题；先复现，再修正并重跑专项。
- 相关 race、vet、构建与 CI 按 NEXT_RELEASE 台账记录；本机夹具不等于真实上游或生产压测。

## 仍然开放的费用边界

上游用量在响应结束时报告。此次检查能在已知余额不足时停止继续转发，但不能阻止当前
响应已经发生的费用；实际费用超过预留时沿用已有负余额结算规则。
不足以取得下一整个窗口时可能提前结束会话，客户端需补充额度后重连。

网络或客户端在 usage 到达前断开，仍可能没有完整用量；不能靠等待 worker 恢复未知账单。
独立音频转录费用、provider 不报告 usage、重复 usage 事件、持久幂等及重启恢复仍待后续设计与验收。
旧 Redis 在途计数不再用于这条新路径；混合部署旧实例不能获得完整新边界，应统一升级。
无 schema 修改。代码回退恢复缺少预留及异步收尾风险；未发布镜像或部署。
