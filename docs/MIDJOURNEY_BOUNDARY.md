# Midjourney 通知与图片读取边界

## 通知是刷新提示

`/mj/notify` 及 `/:mode/mj/notify` 继续使用 `mj-api-secret` 中的普通 One Hub 用户令牌。
该令牌只证明用户身份，不能证明消息由上游服务发送。

- 请求的 `id` 必须属于当前用户；他人的任务、缺失任务、无效令牌均不能触发合法通知。
- 任务所有者的合法通知保留空 HTTP 200 响应，只唤醒既有轮询器。
  `status`、`progress`、`imageUrl`、时间和其他通知字段不直接写入数据库。
- 已完成任务的通知不会重开任务。重复通知不新建轮询 goroutine，也不直接退款。
- 任务状态由存储的渠道配置与渠道凭据向上游拉取；更新是异步的，遵循既有 15 秒轮询节奏。
  上游不可达时，通知成功只表示已接受提示，不能证明任务已同步。

`MjNotifyEnabled` 继续控制用户自定义 `notifyHook` 是否转发给上游，不作为可信上游身份开关。
自定义通知透传、任务查询返回的原始 URL 和现有前端图片使用方式保持原用途。
部署方如果过去依靠普通用户令牌直接写通知状态，需要转为支持绑定渠道的任务查询接口。
本仓库未定义新的可信推送协议，也不接受凭空假定的渠道 Key 反向认证约定。

## 轮询绑定

任务 ID 按渠道分组，同一渠道、同一上游任务 ID 的多条本地记录分别更新。
跨渠道同名任务互不覆盖；缺失渠道按本地行 ID 处理，不以全局上游 ID 批量修改其他渠道。
请求前检查任务与渠道绑定，并继承该渠道配置的代理；响应写入前检查整个批次，拒绝未请求的 ID。
内容完全一致的重复响应只处理一次；同一 ID 的冲突响应拒绝整批写入。
保留正常状态、按钮、属性和既有失败补偿行为；本批不宣称完成多实例退款/支付原子性改造。

## 原始图片读取

`/mj/image/:id` 与模式别名继续提供公开图片读取，不改变为用户登录接口。
每次读取存储的图片 URL 时都应用 [公网下载策略](MEDIA_DOWNLOAD_POLICY.md)，包括历史记录。
正常图片返回完整原始字节；未提供 Content-Type 时仍使用 image/jpeg。
Worker JSON 协议不用于这个原始图片入口，环境代理兼容规则见下载策略。

下载受 15 秒、20 MiB 和请求取消约束，先完成有界读取再返回 200。
目标拒绝、上游非 200、超时或不完整/过大的正文返回固定 502 错误，不透传上游错误正文。
因此成功响应开始时间可能晚于旧的边下边传；每个并发请求的缓冲与上限有关。
不存在的任务保留 400 错误。公开读取的既有权限语义不等于对所有图片隐私场景作出保证。

## 验收与回滚

```sh
go test -race -count=1 ./relay/midjourney ./controller ./model
go test -race -count=1 ./common/image -run '^(TestMedia.*|TestParseBase64File)$'
go vet ./relay/midjourney ./controller ./common/image
```

夹具只使用本机服务和临时 SQLite；真实上游、PostgreSQL 与生产部署另行验收。
没有 schema 或配置迁移。回退代码会重新开放通知直接写入和无限制图片下载，不能作为普通兼容错误的处理方式。
