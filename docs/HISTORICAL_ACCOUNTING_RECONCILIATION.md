# 历史预留和支付歧义的核对规则

源码基线：已合并 `f5c1ad53ef3e2d4b078d55404fc6e4ac4098cca5`（PR #77）。
本节整理现有账务约束与逐笔核对流程；没有读取生产账本，没有批准或执行历史补扣、退款、
充值、删除记录或覆盖状态。历史数据是否存在、数量和实际归属仍未核实，不能据此关闭发布阻断项。

## 先区分记录含义

| 记录状态 | 当前证据能证明什么 | 当前允许的程序行为 | 不能推断的结论 |
|---|---|---|---|
| 预留 `reserved` | 原身份和预留已持久化 | 保持预留，等待确定终局或逐笔核对 | 过期、进程消失、缺日志不证明未调用或可退款 |
| 预留 `pending` | 确定消费/退款意图已持久化 | 现有恢复任务按原意图、原 owner/mode 重试 | 不能用新金额或相反意图替换 |
| 预留 `reconcile` | 观察到不完整用量或响应证据 | 保持预留和快照，不进入自动结算 | KnownQuota 是已知部分，不是最终应付或应退金额 |
| 预留 `consumed/refunded` | 此账本已完成相应事务 | 同意图重放不再改钱；相反意图拒绝 | 不能改回 pending 后重新执行 |
| 任务 `review_required` | 历史预留不存在或身份关联不足 | 保留核对状态 | 任务估算额度不是实际扣款证明 |
| 补偿 `pending` | 已请求逆向补偿 | 原消费可证明且身份完整后走现有幂等事务 | 未解决预留不能当成已消费金额退款 |
| 补偿 `applied/not_charged` | 已补偿，或原账本本来就是退款 | 重放不重复补偿 | 不抹掉原消费历史与补偿轨迹 |
| 支付 `pending/closed` | 本地未确认成功；closed 只是本地过期 | 原渠道完整验证后的合法成功通知可结算一次 | 超时、空响应、三小时关闭不证明平台未支付 |
| 支付 `success` 且有结算标记 | 在当前事务约束下已登记成功 | 相同事实/流水重放幂等 | 单看 status 不足以证明旧版本已记余额 |
| 历史 success 无标记、failed 或事实冲突 | 无法按当前自动入口证明可安全入账 | 拒绝自动补款，逐笔核对 | 不能补写 settled_at 或 claims 来制造已结算证明 |

依据：`model/quota-reservation.go`、`model/quota-compensation.go`、
`model/quota-reconciliation.go`、`model/order.go`。当前恢复任务仅查询 `pending` 终局，
另行恢复已登记补偿；它不会按记录年龄退款，也不会自动处理 `reconcile`。

## 归属以原始关联为准

预留核对 `id → user_id / token_id / unlimited_quota / channel_id / model_name`。
HTTP request_id 只是关联线索；Search 子调用、不同账本、同额请求不能据此合并。
原有限/无限令牌模式来自预留快照。令牌已经转移或删除、用户不存在时保持待核对，
不得向当前同名用户、新令牌 owner 或另一个账户补扣/退款；也不临时改归属以通过检查。

任务补偿还需核对任务的 reservation_id、原 user/token/channel 与账本一致，并证明原消费。
没有账本的旧任务即使保存了估算费用，也不能自动建立一笔“已扣款”记录。

支付核对原订单、原 gateway_id、商户事实、订单总金额（整数分）、币种及协议提供的用户标识。
流水唯一范围是同一 gateway_id 下的完整平台流水号；不能只比较尾号、展示截断值、用户名或金额。
`order_payment_claims` 与未建立该表前的订单都参与归属，包括软删除订单。
同一流水命中不同订单，即使其中一笔已软删除，也不能从另一笔重新认领。

网关停用/软删除与签名凭据失效不是同一事件：已发起订单可使用保留的原配置验证延迟通知。
硬删除配置或无法取得可验证事实时，不能借用新渠道密钥、猜测历史密钥或只相信截图。

## 逐笔工作单与证据边界

建立受控工作单，至少记录以下内容；公共 PR 只保留合成例子和汇总状态：

- 工作单 ID、核对时间、受检程序 SHA/实际版本、数据库类型和恢复点。
- 账本/订单/任务的内部主键、原身份 ID、当前状态与修订号、预留/确定金额、补偿状态。
- 关联证据的位置、获取时间、摘要和来源；支付商户/流水引用在公开输出中脱敏。
- 已确认事实、缺失事实、冲突记录、可能仍在运行的请求或在途回调。
- 拟处理规则、精确影响的记录集合、用户/令牌余额及日志/统计的预计变化。
- 对应批准、执行结果、重试/重复执行结果和执行后核对；无法判定的保持开放。

初次盘点只读取最小字段，不读取 token key、渠道密钥、完整提示词、事件内容或全部用户表。
按稳定主键分页，建议每页不超过 100 行；包含软删除归属记录，不能依赖普通管理页面的过滤结果。
金额、身份与状态应取自同一只读快照，不能把多次跨时刻查询拼成一笔已确认交易。
账户余额差额、单条消费日志、业务截图、缓存值和时间顺序均不能独自证明历史归属。
生产读取权限、备份与恢复点在生产核实步骤单独核对；本文没有执行那些步骤。

## 处理规则

1. **可恢复且有确定意图**：先核对主体完整、原身份与金额一致，再观察既有恢复机制的结果。
   不直接 UPDATE 余额、终局字段或修订号来代替事务。恢复失败保留原错误和记录。
2. **正常支付事实齐全**：仍经过供应商验证与共享订单事务入口。`SettleOrderPayment` 接收的是
   已验证事实，不是让管理员跳过验签的手动充值 API；不能直接调用它伪造通知。
3. **确定已消费后的任务补偿**：只沿现有原账本关联与幂等补偿流程；原请求计数/历史保留，
   新增补偿日志，不把原消费改写成未发生。身份、金额或溢出校验失败停止该项。
4. **未知、冲突或缺乏旧版本证据**：只形成拟处理方案，不自动选择退款、补扣、充值或归零。
   对外平台付款事实与本地是否已入账要分别证明；存在两种合理解释时继续保留歧义。
5. **确需人工调整**：当前源码没有通用、经审阅的历史核销接口。先完成精确记录、业务依据、
   身份归属、金额、幂等键、并发约束、审计记录及回滚数据决策，再作为独立变更验收和批准。
   维护授权不等于已批准某笔真实资金调整；不能以直接 SQL 清理代替这一缺失实现。

数据库备份回滚会影响恢复点后的其他写入。它不能作为单笔错误调整的默认撤销办法；
不得通过恢复旧状态让已入账通知再次执行。并发执行前还须核对仍运行的旧实例和在途回调，
新旧混用可能绕过新账本约束，单节点源码正确不等于生产已完成升级。
