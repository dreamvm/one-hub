`1970ec148bea899e7861a1e161bc7161a7e58288`。候选版本仍为
`v0.14.27-dreamvm.1-rc.8`，未打标签、发布或部署。

## 账务边界

原 `sync.Once` 只保护一个内存对象，失败后不能重试，进程消失后没有预留凭据。
余额、统计、日志分开写入，batch 的内存队列也不能作为持久恢复依据。

新增 `quota_reservations` 表。每个 Quota 生成独立随机 ID；HTTP request ID 仅用于关联，
Search 子调用和 MJ 替换模式不会共用同一账务 ID。账本固定用户、令牌、预留时无限模式、渠道和模型，
记录累计预留与最终费用。没有令牌 key、提示词、上游凭据。

- 预留行与账户/有限令牌预扣同事务；无限令牌按原模式处理。
- Realtime 续额使用绝对目标，重放相同或旧目标不会再次扣款或释放预算。
- 免费请求记录零金额账本，原费用仍为零。
- `reserved` 只证明预留存在；`pending` 表示确定的消费/退款意图已经持久化。
- 终局事务同时更新账户、有限令牌、用户/渠道统计、启用的消费日志以及 `consumed/refunded` 状态。
  此路径不再进入旧内存 batch 队列，batch 开关不削弱原子性。
- 同一编号的重复终局只返回既有结果；相反结果或不同金额不能覆盖已选择意图。
  不同编号即使金额相同，也按不同请求计费。
- 多实例通过数据库写锁串行化同一账本；不依赖 Redis 或进程锁实现账务幂等。
- 关闭消费日志时不在账本保存日志内容；终局完成同事务清空临时日志快照，避免日志清理后另留副本。

原无 ID 的 Pre/Post 函数作为兼容接口保留原语义，不能据此声称它们自身具有持久幂等。
共享 relay 已使用新账本 API；后台失败补偿在下一批单独接入。

## 恢复与不能自动推断的情况

每个实例启动恢复任务，每 15 秒处理最多 100 个待恢复项；同一 pending 可由多个实例安全重放。
数据库不可用期间，确定的终局在当前进程保留不可变快照并继续尝试持久化，不保留 Gin 对象。
快照成功落库后，重启只需读取数据库即可恢复；不需要原 Quota、原响应或原调用者再次请求。

**终局意图尚未落库且进程同时崩溃时，用量仍不能凭空恢复。** 此时保留原 `reserved`，等待核对。
只有预留、没有确定终局的记录绝不按超时自动退款。上游漏报/重复用量、失联时是否已计费、
旧版本已丢失的预留及异步任务保存失败，也不能靠余额差额猜测。

令牌已删除或换归属、账户已删除等主体不完整情况保留 pending，记录失败状态，
不把旧请求费用或退款写入新 owner。预留后的无限模式切换按原模式结算。
没有已批准的业务证据时，不通过直接改状态来“清空”待核对账目。

只读排查可按数据库权限查看最小字段：

```sql
SELECT id, user_id, token_id, model_name, state, outcome,
       reserved_quota, final_quota, created_at, updated_at, failure_code
FROM quota_reservations
WHERE state IN ('reserved', 'pending', 'reconcile')
ORDER BY created_at;
```

`reserved` 也可能是仍在运行的请求，不能仅凭年龄判断上游未计费。
记录保留/归档策略、待核对管理界面和历史人工核账不是本批的自动资金操作。

## 验证与兼容

- 旧实现的数据库恢复后 Consume/Undo 重试失败已先复现，再验证新实现恢复。
- 三数据库套件增加 34 个账本叶用例，总计 88 个：重复/冲突命令、独立同价请求、
  免费及退款、六处写入故障完整回滚、重新打开 DB 恢复、16 个并发执行者、续额重放、
  未知预留保持、owner/mode 变更及日志关闭。
- 本地 SQLite 与 PostgreSQL 88 项事务专项及相关包 race、vet、编译、工作流检查通过。
  PostgreSQL 初次夹具批量迁移触发既有 Log/Channel 关联顺序问题；改为与应用相同逐表迁移后通过，
  没有关闭外键检查。完整 PostgreSQL 应用启动/E2E 仍留在后续工程验收。
- 一次独立审阅确认意图首次写入失败后不可见、完整日志副本保留两项问题；
  失败回归后加入已知意图重试和终局快照清理，再运行相关验证。
- 缺少新表时 Search 在调用上游前拒绝；不会静默退回旧扣款。
- MySQL、精确提交 CI 及隔离镜像升级/回滚以 PR 和 NEXT_RELEASE 的后续记录为准。

迁移为新增表，由 master 的可检查 AutoMigrate 创建；先完成迁移再启动依赖该表的节点。
旧进程不使用账本，不应把新旧混合运行视为完整幂等覆盖。回退代码前须核对 pending/运行中请求；
旧镜像不会自动恢复新账本。恢复数据库备份仍会丢失恢复点之后的写入，需独立数据决策。
本批不自动删除账本、不回填猜测的历史记录、不补扣历史费用。

## Realtime 缺失报告的待核对状态

后续修复增加 `reconcile` 状态及隐藏于普通 JSON 的 `reconciliation_data` TEXT 列，
详见 [REALTIME_MISSING_USAGE.md](REALTIME_MISSING_USAGE.md)。它保存已观察用量和计价快照，
不代表最终消费或退款；`outcome` 为空，`final_quota` 不得作为已知总费用使用。
既有恢复任务只自动完成 `pending`，不会把 `reconcile` 自动扣款或退款。
读取证据须使用受控数据库权限；没有新增公开读取或核销接口。

迁移须先于新节点启动。回退前核对运行中请求和 `reserved/pending/reconcile`；
保留新列与记录，不执行删除列或强制改状态。旧账本实现忽略该状态，旧 Realtime
解析器不保护新连接的缺失报告；混合运行和回退后的业务正确性尚未完成最终验收。
