# C2a：模型层额度事务

`PreConsumeTokenQuota` 和 `PostConsumeTokenQuotaWithInfo` 的账户余额与有限令牌
remain/used 额度，在一个数据库事务内即时更新。batch 开启时也不排入延迟余额队列；
请求数、用户/渠道消耗统计和日志仍使用既有路径，不属于本事务。

## 保证与兼容

- 正数预扣先对用户执行 `quota >= amount` 条件更新，再对有限令牌执行
  `remain_quota >= amount` 条件更新。统一按用户→令牌顺序加锁，失败则整笔回滚。
- 初读令牌的 owner/mode 在事务内再次约束；无限令牌使用锁定读取验证，账户照常扣款，
  令牌额度字段不变。每个非零更新必须恰好影响一行，不能把缺失行记作成功。
- Post 接受有符号差额：正数补扣、负数退款、零数无操作。实际使用超过预估时允许余额为负，
  保留已消费账目，因此本项不是完整请求额度上限。Pre 负数拒绝、零数无操作。
- 已禁用/过期令牌仍可结算或退款已发生消费；新请求是否授权由鉴权层负责。
  用户或令牌不存在、被软删除、或令牌已转移归属时，整笔拒绝，不跨归属记账，
  不自动恢复删除记录。这时原预留保留，需要独立核对，不能声称自动补偿完成。
- Post 继续采用调用方保存的 unlimited 模式；不以结算时的新模式改写旧预留。
  认证→预扣→终结之间模式/归属变化仍需后续真实预留凭证解决，本项不关闭该跨阶段问题。
- 低余额邮件只在事务提交成功后触发，使用事务内读出的用户快照。

## 仍开放的边界

只保证进入这两个方法的单次数据库操作；高余额跳过预扣、Redis 先减后失败的补偿及缓存刷新、
Search 先调用上游后检查、实时会话额度、超预估消费策略、持久幂等及进程崩溃恢复仍开放。
其他 `Increase/Decrease*Quota` 使用者（奖励、支付、后台任务补偿等）未纳入事务；
同一 Quota 的终结失败仍不重放，后续恢复必须避免重复退款。完整 C1/C2 继续阻断正式版。

## 验证

`model/quota-transaction_test.go` 覆盖有限/无限、batch 开/关、扣款/退款故障回滚、
缺失/软删除/转移归属、事务前模式变化、精确耗尽、超预估结算和并发共享余额。
同时断言 flush 前已落账、flush 后不重复扣款。并发使用 8 个连接、24 个请求，
分别竞争同一 Token 或多个 Token 的同一账户；95 额度每次预扣 10，只允许 9 次。

默认使用临时 SQLite；CI 在一次性 MySQL（InnoDB）和 PostgreSQL 服务中执行相同专项：

```sh
go test -mod=readonly -race -count=1 -timeout=120s ./model -run '^TestQuotaTransaction'
# 仅在已准备的隔离服务上显式选择；地址/库名固定，不读取应用 DSN。
ONEHUB_QUOTA_TEST_DB=mysql go test -mod=readonly -race -count=1 -timeout=120s ./model -run '^TestQuotaTransaction'
ONEHUB_QUOTA_TEST_DB=postgres go test -mod=readonly -race -count=1 -timeout=120s ./model -run '^TestQuotaTransaction'
```

测试表使用独立前缀，结束后清理；测试凭据仅用于本机临时服务。CI 固定数据库镜像摘要，
没有真实模型或支付请求。实际通过结果按候选 SHA 记录，不能将 CI 配置存在等同于执行成功。
SQLite 忙错误、数据库事务失败均返回错误并回滚，不自动重试；未完成生产负载测试。

## 升级与回退

没有 schema 变更，但关键余额写入从批量转为同步事务，会增加数据库写入量。
旧进程仍可能持有未落库增量，升级前必须停止入流量、等在途请求结束，确认旧批量周期
成功刷完再退出；不要混用仍延迟扣款的旧进程。新版本无法恢复旧进程已丢失的队列。
回退代码会恢复竞争透支和半笔写入风险，不能作为账目修复手段。本轮不执行生产升级。
